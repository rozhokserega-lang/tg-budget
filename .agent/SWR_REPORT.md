## Подтверждённые проблемы

| Проблема | Причина в исходном коде | Влияние | Решение |
| --- | --- | --- | --- |
| Повторные запросы планов | openPlans всегда вызывает loadPlans(true) | 2 запроса при каждом входе | Обычный вход соблюдает TTL; принудительные обновления сохранены |
| Категории обходят TTL | loadCategories сразу возвращает st.categories | Устаревание до явного refresh | Кэш с TTL, stale данные сразу, обновление в фоне |
| Избыточная отрисовка финансов | openTx рисует previous и затем тот же результат loadTx | Повторная замена DOM | Переиспользование одинаковых JSON и проверка идентичности |
| Сброс прокрутки и анимаций | renderContent обнуляет scrollTop, новые узлы запускают CSS-анимации | Рывки при background refresh | Сохранение scroll/focus, подавление анимаций фоновой перерисовки |
| Потеря текста до debounce | Поиск сохраняется в state только через 120 мс | Ответ сети может заменить введённый текст | Черновик сохраняется сразу, фильтрация остаётся отложенной |
| Глобальная очистка при add/edit | clearCache очищает все месяцы и ресурсы | Повторная загрузка независимых данных и skeleton | Инвалидация tx/summary только затронутых месяцев, stale остаётся доступным |
| Нет серверного пересчёта после delete | Подтверждение лишь снимает deletingTx | Доли партнёров остаются локальным приближением | Инвалидация месяца и актуализация активной страницы после подтверждения |
| Короткая блокировка lifecycle | refreshOnReturn завершается после запуска, не окончания загрузок | Повторный lifecycle сигнал может запустить лишнее обновление | Ожидание общего promise с pull refresh |
| Общий promise refresh для разных страниц | pageRefresh не учитывает месяц/страницу/аккаунт | Refresh новой страницы может присоединиться к устаревшему | Контекст страницы, месяца, seq и scope; старый callback не снимает новый индикатор |
| Возврат во время редактирования пропускает синхронизацию | Проверка editingTx прекращает refreshOnReturn | Изменения партнёра не подтягиваются | Обновляется основная страница; sheet, draft и inert сохраняются |
| Откат удаления затирает параллельные изменения | Восстанавливается полный старый snapshot сводки | Суммы теряют изменения других операций | Компенсация только конкретной операции без дубликатов |
| Откат add очищает независимые данные | removeOptimisticTx вызывает глобальную очистку через removeLocalTx | Потеря кэша и риск потери других optimistic записей | Удаляется только неуспешная запись, сводка корректируется дельтой |
| Старый DOM при смене scope | adoptMember очищает данные, но не экран/отложенный fade | Кратковременный показ старой семьи | Очистка экрана и отмена устаревшей отрисовки |

Дедупликация одинаковых запросов, TTL расходов/сводки, epoch/scope защита и сохранение кэша при сетевых ошибках уже работали. Их архитектура сохранена. Для адресной инвалидации добавлены версии ключей, включая защиту перед commit в state.

## Изменённые файлы

- `src/cache.js`: invalidate(keys) сохраняет stale; равные JSON сохраняют ссылку и обновляют TTL. Полная invalidate()/setScope() по-прежнему удаляют всё.
- `src/app.js`: TTL/SWR планов и категорий; адресная инвалидация add/edit/delete; reconciliation серверного ID; независимые откаты; coalescing lifecycle/pull; полное обновление финансов (включая статистику); сохранение scroll/search/focus/sheet; запрет старой страницы и scope.
- `styles/finance.css`: только отключение повторной анимации карточек/прогресса планов при фоновой перерисовке.
- `tests/cache.test.cjs`, `tests/app.test.cjs`: 17 новых тестов; обновлены ожидания двух существующих сценариев под сохранение stale вместо удаления снимков.
- `tests/swr-performance.cjs`: воспроизводимый benchmark на существующем VM DOM harness.
- `.agent/STATE.md`, `TASKS.md`, `HANDOFF.md`: контрольная точка; этот отчёт.

API, очередь хранения, навигация, дизайн и зависимости не изменены. Нового localStorage/IndexedDB, WebSocket или polling нет. Глобальный clearCache оставлен для смены аккаунта и общих мутаций с более широкими зависимостями.

## Сравнение до/после

Node VM, production cache/controller/views, искусственный API, счётчик записей screen.innerHTML. Это не измерения browser layout/paint, FPS или времени ответа реального сервера. До: отдельный worktree исходного commit. После: финальное состояние ветки; один и тот же benchmark.

| Сценарий | До | После |
| --- | ---: | ---: |
| Открытие финансов со свежим кэшем: API | 0 | 0 |
| Открытие финансов со свежим кэшем: полные замены DOM | 2 | 1 |
| Принудительное обновление с теми же данными: API | 1 | 1 |
| Принудительное обновление с теми же данными: полные замены DOM | 2 | 0 |
| Повторный вход в планы: API | 2 | 0 |
| Холодная главная: API без boot/me | 4 | 4 |
| Холодная главная: полные замены DOM, включая skeleton | 3 | 2 |

Задержка API 300 мс: кэш 2.79 → 2.34 мс; свежие данные 304.74 → 303.51 мс.

Задержка API 1000 мс: кэш 1.41 → 0.73 мс; свежие данные 1003.12 → 1002.66 мс.

Кэш отображается синхронно до завершения сети в обоих вариантах. Малые различия времени единичного прогона не доказывают ускорение CPU. Основной подтверждённый выигрыш — меньше запросов и замен DOM. Время получения свежих данных по-прежнему определяется сетью.

## Риски и готовность

- Реальные Telegram Android/iOS, browser layout/paint, жесты, клавиатура и визуальные регрессии требуют ручного прогона. Playwright установлен, но исполняемый browser engine отсутствует; браузерная проверка не выполнена.
- Supabase и два реальных аккаунта не использовались: партнёрские изменения и сетевые гонки проверены управляемыми API заглушками.
- **Существующий api.js запрещает updateTx вне demo (`update_unsupported`).** Изменение даты и обновление обоих месяцев проверены через адаптер в тестах. Серверное редактирование потребует отдельного подтверждённого backend-контракта; это ограничение не обходилось.
- JSON comparison линейно зависит от объёма ответа; большие production-выборки и низкопроизводительные устройства не профилировались.
- Существующая персистентная Queue не менялась; новая работа не добавляет постоянное хранение финансов. Восстановление офлайн-очереди после перезапуска/смены реального аккаунта этим VM harness не проверяется.

Решение готово к code review и интеграции в main с указанными ограничениями. Перед релизом нужен ручной Telegram smoke test. Изменения остаются в локальной ветке; публикации нет.
