# Платежи: интеграция frontend и backend

Канонический HTTP-контракт: [FRONTEND_API_CONTRACT.md](api/FRONTEND_API_CONTRACT.md), OpenAPI 1.1.0. Реализация сервера — отдельный репозиторий `tg-budget-app`; клиент — `src/payments-rest.js`.

## Транспорт

В Telegram `PaymentsApi` выбирает REST-адаптер; вне Telegram/с `?demo` — mock в памяти. Ошибка сервера не переключает реальные операции на mock. `APP_PAYMENTS_ADAPTER` остаётся опциональной точкой внедрения для тестов и других сред.

Базовый URL — `Api.url + /v1`, авторизация `Authorization: tma <initData>`. Семья и участник определяются сервером: локальный `scope` не передаётся в HTTP. Авторизация фиксируется на всю загрузку страниц календаря.

| Метод UI | HTTP |
| --- | --- |
| list | Все страницы `GET /payment-templates` и `GET /payments?from&to` |
| save | `POST /payments` или `PATCH /payments/{id}` |
| pause | `POST /payments/{id}/pause` или `/resume` |
| remove | `DELETE /payments/{id}` |
| confirm | `POST /payment-occurrences/{id}/confirm`, `Idempotency-Key` |

Локальные поля `name/amount/category_id/date/repeat/reminders/overdue_every` преобразуются в `title/plannedAmount/categoryId/firstDueDate/recurrenceRule/notificationRules/overdueNotificationRule`. Идентификаторы начислений берутся с сервера; клиент не строит их по дате. Оплаченные строки скрываются, просроченные вне выбранного месяца сохраняются.

Редактирование отправляет только изменённые поля и исходную `version`. Настройки времени, дней недели, валюты и числа повторных уведомлений сохраняются. Версия берётся из снимка при открытии формы. Даты 2000–2100, название до 120, описание до 1000 символов, сумма до 1e9; повтор дней/недель до 365, месяцев до 12, лет до 10; уведомления за 0–30 дней, повтор просрочки через 1–30 дней. Новые уведомления: 10:00 по таймзоне семьи, до 5 повторов при просрочке. Новая валюта берётся из текущей настройки интерфейса; существующая не переименовывается и не конвертируется. Календарь не складывает разные валюты в один итог.

Confirm — один серверный запрос, отдельный `add_tx` не вызывается. Повтор того же содержимого сохраняет ключ в текущем сеансе; изменение суммы/даты/категории получает новый ключ. От перезагрузки и одновременной оплаты партнёрами защищает уникальность начисления на сервере. После подтверждения очищается существующий кэш календаря и финансов.

## Порядок публикации

1. Сначала обновить Edge Function `api` до контракта 1.1.0 с `GET /payment-templates`. Новых миграций для этого изменения нет. Маршрут нужен для пауз и шаблонов без начислений.
2. Проверить health, 401 без initData, старые операции и новый список с авторизацией.
3. Затем публиковать клиент, проверять в Telegram: создание → оплата → один расход, повтор оплаты, пауза/возобновление, удаление и прекращение уведомлений.

Миграции 018–022 и cron по памяти проекта уже применены; перед production сверять фактическое состояние. Legacy recurring не переносится клиентом повторно. Напоминания и задачи пока имеют страницы ожидания.
