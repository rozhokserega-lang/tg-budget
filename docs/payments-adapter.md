# Платежи: интеграция frontend и backend

Статус: frontend с mock-адаптером. **Согласованного нового Backend-контракта в задаче и репозитории нет.** Проверены main `tg-budget` (401379b) и `tg-budget-app/supabase/functions/api/index.ts`: прежние list_recurring/save_recurring/pay_recurring не покрывают новые требования. Следующий интерфейс — локальная граница frontend, предложение для согласования, а не утверждённый HTTP-контракт.

Реальный режим намеренно недоступен до подключения адаптера. Mock используется только при Api.isDemo(), живёт в памяти до перезагрузки и не отправляет Telegram-уведомления. Автоматического fallback на mock после ошибок реального API нет.

## Подключение

Перед загрузкой app.js установить `window.APP_PAYMENTS_ADAPTER` с асинхронными методами ниже. Конкретные URL/actions определяет backend-разработчик после согласования. Не направлять методы на старые recurring endpoints. UI использует один и тот же интерфейс для mock и сервера.

| Метод | Аргументы | Результат |
| --- | --- | --- |
| list | `{scope, month: 'YYYY-MM'}` | `{payments: Payment[], occurrences: Occurrence[]}` |
| save | `{scope, payment: PaymentInput}` | `Payment` |
| pause | `{scope, id, paused: boolean}` | `Payment` |
| remove | `{scope, id}` | `{ok: true}` |
| confirm | `{scope, occurrence_id, amount, paid_on, category_id, idempotency_key}` | `{occurrence_id, transaction}` |

`scope` — локальный ключ member:household для кэша и защиты от старых ответов. Сервер **не должен** доверять этому ключу для авторизации: определять семью и участника по проверенному Telegram initData. Доступ к общей семье у обоих партнёров одинаковый.

PaymentInput: `{id?, name, description, amount, category_id, date: 'YYYY-MM-DD', repeat: null | {unit: 'day'|'week'|'month'|'year', interval: integer 1..365}, reminders: integer[] (0..365, до 10), overdue_every: null | integer 1..365}`. Amount — положительное число до двух десятичных знаков. Категория — expense из существующего справочника. Даты 1900..2100. Payment добавляет `{id, paused}`. Mock дополнительно хранит внутренние интервалы пауз, UI их не передаёт.

Occurrence: `{id, payment_id, due_on, name, description, amount, category_id, status?}`. ID начисления стабилен при обновлении/редактировании/паузе. Оплаченные начисления не возвращаются. Для календаря вернуть активные начисления выбранного месяца **и все более ранние неоплаченные** (включая просрочки за пределами месяца). Future projections должны иметь стабильные ID, подтверждение до срока поддерживается. `status: 'paused'` можно передать для приостановленного будущего начисления; overdue/today вычисляются по due_on. Поля каждого начисления самостоятельны: редактирование серии сохраняет уже возникшие обязательства.

## Обязательные гарантии backend

- Confirm — одна транзакция: блокировка начисления, проверка семьи, запись оплаты и ровно одного связанного общего расхода. Уникальность по occurrence_id, включая одновременное подтверждение разными партнёрами с разными ключами. Повторный запрос возвращает исходный результат.
- Idempotency key сохраняется frontend при повторе в текущем сеансе. После перезагрузки защиту обеспечивает серверная уникальность occurrence_id. Не заменять confirm двумя запросами и не помещать его в обычную очередь add_tx.
- Фактическая сумма меняет только текущую оплату, план серии не меняется.
- Сервер хранит возникшие начисления независимо от расписания. Пауза не удаляет долг, возобновление не начисляет пропущенные во время паузы периоды.
- Для месяцев/лет сохраняется исходный якорь: 31 января → 28/29 февраля → 31 марта; 29 февраля → 28 февраля невисокосного года → 29 февраля високосного.
- Определить и согласовать timezone семьи для наступления дат и времени уведомлений. Mock использует локальную дату браузера; расчёты повторов date-only через UTC.
- Настройки уведомлений относятся к серии. Backend отправляет обоим партнёрам; подтверждение прекращает отправку по начислению. Frontend не планирует таймеры уведомлений.
- Remove удаляет определение и неоплаченные начисления, но не расходы. Это явно указано в подтверждении.
- Ошибки отклоняют Promise с `{code, message}`; конфликты/валидация/нет доступа не маскируются успешным ответом. Поля message показываются как текст.

После мутации frontend инвалидирует существующий кэш приложения, очищает развёрнутую категорию и перечитывает календарь. При следующем открытии финансов выполняется загрузка актуальных расходов. Возврат в Mini App и pull-to-refresh перечитывают текущий календарь; реальные партнёры синхронизируются через сервер, не через mock. SSE/Realtime не добавлялись.

## Незавершённые интеграции

Нужны согласованный транспорт/API, миграции и серверная атомарность, Telegram-уведомления, timezone. Напоминания и трекер открывают отдельные страницы ожидания: их реализация относится к другим агентам. Старые goals/debts/wishes/recurring данные сохранены; автоматической миграции recurring → Payments нет. Перед production нужно согласовать миграцию, поскольку прежние разделы и баннеры скрыты интерфейсом.
